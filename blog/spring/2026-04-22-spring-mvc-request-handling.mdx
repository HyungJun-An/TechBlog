## Spring MVC 요청 처리 전체 흐름

요청 하나가 들어와서 HTML로 응답하기까지, 스프링 내부에서 어떤 컴포넌트가 어떤 순서로 동작하는지 직접 확인해보세요.

<MVCFlowViz />

핵심은 **DispatcherServlet이 모든 요청의 중앙 관제소**라는 점입니다. 요청을 직접 처리하지 않고 HandlerMapping → HandlerAdapter → Controller → ViewResolver로 위임합니다. 이 구조 덕분에 컨트롤러 코드는 HTTP 처리 세부사항을 알 필요가 없습니다.

## 컨트롤러 기초: @Value, @GetMapping, Model

### @Value — 설정값 주입

소스코드에 하드코딩 대신 `application.properties`에서 값을 읽어옵니다.

```java
// application.properties
app.title=Spring Board

// Controller
@Value("${app.title}")
private String appTitle;

@GetMapping("/")
public String index(Model model) {
    model.addAttribute("title", appTitle);
    return "index";
}
```

### Model vs HttpServletRequest

| 항목 | `Model` | `HttpServletRequest` |
|---|---|---|
| 소속 | Spring MVC | Jakarta Servlet (톰캣 계층) |
| 사용 목적 | 뷰에 데이터 전달 | 요청 정보 직접 접근 |
| 코드 의존성 | Spring에만 의존 | Servlet API에 의존 |
| 권장 여부 | ✅ 컨트롤러에서 권장 | 필터/인터셉터에서 직접 사용 |

> `Model`은 내부적으로 `HttpServletRequest`의 attribute로 변환되어 뷰로 전달됩니다. 같은 동작이지만 Spring 방식이 더 테스트하기 쉽습니다.

## void 반환 시 뷰 이름 결정 규칙

반환 타입이 `void`이면 스프링은 **요청 URL 경로**를 뷰 이름으로 사용합니다. 메소드명이 URL 마지막 세그먼트와 같을 때 "메소드명 = 뷰 이름"처럼 보이는 이유가 이것입니다.

<VoidReturnTester />

```java
@Controller
@RequestMapping("/user")  // 클래스 레벨
public class UserController {

    // URL: /user/login → 뷰 이름: user/login → templates/user/login.html
    @GetMapping("/login")
    public void login(Model model) {
        model.addAttribute("msg", "로그인 페이지입니다.");
        // return 없음 → URL 경로로 뷰 탐색
    }
}
```

> 회사 코드에서 `void` 반환이 보인다면 "뷰가 없는 것이 아니라 뷰 이름 결정 방식이 다를 뿐"이라고 이해하면 됩니다.

## 파라미터 바인딩 4가지 패턴

폼/쿼리스트링 값을 컨트롤러에서 받는 방법은 상황에 따라 다릅니다.

<ParamBindingCompare />

### 다중값 바인딩 — 체크박스

```java
// 체크박스 다중 선택: name="hobby" value="read", "swim", "code"
@PostMapping("/profile")
public String profile(
    @RequestParam(value = "hobby", required = false) List<String> hobbies,
    Model model
) {
    // 과거: request.getParameterValues("hobby") → String[]
    // 스프링: List<String>으로 직접 바인딩
    model.addAttribute("hobbies", hobbies);
    return "profile";
}
```

### DTO vs Map 선택 기준

| 상황 | 권장 방식 |
|---|---|
| 입력 필드가 정해진 폼 | DTO 오토바인딩 (구조화, 재사용 용이) |
| 필드가 동적이거나 일부만 입력 | `@RequestParam Map` |
| 페이징/검색처럼 기본값 필요 | `@RequestParam` + `defaultValue` |
| MyBatis parameterType 미지정 시 | DTO, Map 둘 다 동작 |

## 엔드포인트 설계: 클래스 레벨 @RequestMapping

클래스 레벨에 공통 경로를 두면 컨트롤러 단위로 URL 그룹이 명확해집니다.

```java
@Controller
@RequestMapping("/user")  // 이 컨트롤러의 모든 URL은 /user/... 로 시작
public class UserController {

    @GetMapping("/login")     // /user/login GET
    public void login() {}

    @PostMapping("/login")    // /user/login POST
    public String doLogin(UserDTO dto, RedirectAttributes attrs) {
        // 로그인 처리 후 리다이렉트
        attrs.addAttribute("name", dto.getName());
        return "redirect:/user/myPage";
    }

    @GetMapping("/myPage")    // /user/myPage GET
    public void myPage() {}
}
```

### 경로 변수 설계 주의사항

| 설계 | 문제 | 권장 여부 |
|---|---|---|
| `@GetMapping("/{action}")` | `/user/login2`, `/user/test`, `/user/abc` 등 **모든** 문자열 흡수 | ❌ 의도치 않은 매핑 |
| `@GetMapping("/login")` 고정 경로 | 명확히 1:1 매핑, 예측 가능 | ✅ 기본 권장 |
| `method={GET, POST}` 복수 메소드 | 한 메소드로 GET/POST 모두 처리 | 필요 시만 사용 |

```java
// 나쁜 예: /{action}은 모든 문자열을 잡아버림
@GetMapping("/{action}")
public String dispatch(@PathVariable String action) {
    if ("login".equals(action)) return "user/login";
    // ... 분기가 늘수록 유지보수 곤란
}

// 좋은 예: 명시적으로 분리
@GetMapping("/login")
public void login() {}

@GetMapping("/logout")
public String logout() { return "redirect:/"; }
```

### 코드 비교

// ✅ RedirectAttributes.addAttribute() — 쿼리스트링 자동 변환
@PostMapping("/save")

## @PathVariable — 경로 기반 값 바인딩

`/users/{id}`처럼 경로 세그먼트를 변수로 받습니다. REST API 설계에서 리소스 식별자에 주로 사용됩니다.

```java
@Controller
@RequestMapping("/board")
public class BoardController {

    // /board/detail/42 → seq = 42
    @GetMapping("/detail/{seq}")
    public String detail(@PathVariable int seq, Model model) {
        model.addAttribute("board", boardService.getDetail(seq));
        return "board/detail";
    }

    // 복수 경로 변수
    // /board/2024/spring → year = 2024, category = "spring"
    @GetMapping("/{year}/{category}")
    public String archive(
        @PathVariable int year,
        @PathVariable String category,
        Model model
    ) {
        model.addAttribute("list", boardService.getArchive(year, category));
        return "board/archive";
    }
}
```

> **주의:** `/{category}` 같은 단일 변수를 인덱싱 위치(앞 세그먼트)에 두면 `/board/list`, `/board/save` 등 모든 요청을 흡수합니다. 경로 변수는 **후위 세그먼트**에서 필요한 범위만 사용하세요.

// DAO 호출 공통 로깅 AOP
@Aspect @Component
public class DaoLoggingAspect {

    // *Dao로 끝나는 인터페이스의 모든 public 메소드 대상
    @Pointcut("execution(public * ..*Dao.*(..))")
    public void daoMethods() {}

    @Before("daoMethods()")
    public void logBefore(JoinPoint jp) {
        log.info("[DAO] {} / args={}",
            jp.getSignature().getName(),
            Arrays.toString(jp.getArgs()));
    }

    @AfterReturning(pointcut = "daoMethods()", returning = "result")
    public void logReturn(Object result) {
        log.info("[DAO 반환] {}", result);
    }

    @AfterThrowing(pointcut = "daoMethods()", throwing = "e")
    public void logException(Exception e) {
        log.error("[DAO 예외] {}", e.getMessage());
    }
}

## 한눈에 정리

| 기술 | 핵심 포인트 |
|---|---|
| **DispatcherServlet** | 모든 요청 관문 → HandlerMapping → HandlerAdapter → Controller → ViewResolver 위임 |
| **@Value** | `application.properties` 값을 필드에 주입, 소스 하드코딩 방지 |
| **Model** | HttpServletRequest 위에서 동작하는 Spring MVC 뷰 데이터 컨테이너 |
| **void 반환** | 요청 URL 경로 = 뷰 이름, 메소드명과 일치시키는 것이 관례 |
| **DTO 오토바인딩** | 폼 name = DTO setter → 형변환 자동, setter 없으면 바인딩 실패 |
| **@RequestParam 옵션** | `defaultValue`로 기본값, `required=false`로 선택 파라미터 처리 |
| **redirect:** | 새 HTTP 요청 → Model 데이터 소멸, RedirectAttributes 또는 쿼리스트링으로 전달 |
| **@PathVariable** | 경로 세그먼트를 변수로 바인딩, 앞 세그먼트 단독 변수는 모든 요청 흡수 주의 |
